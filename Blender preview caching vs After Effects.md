# Blender Caches Data, After Effects Caches Frames

Only partly. Blender has no equivalent of After Effects' preview cache for the 3D Viewport. The viewport stores no rendered frames: every frame re-evaluates the scene and redraws it, and the design task for automatic animation caching (#73481) is still an unassigned, unvalidated design as of October 2026 ([#73481](https://projects.blender.org/blender/blender/issues/73481)). Blender does have AE-style RAM previews in its 2D editors. The Video Sequence Editor (VSE) has a RAM cache with prefetch and a timeline indicator. The interactive compositor gains a playback "Frame Cache" in 5.3, which is in beta now ([PR #159902](https://projects.blender.org/api/v1/repos/blender/blender/pulls/159902)). Neither has a persistent disk cache, because **the VSE disk cache was removed in Blender 4.5** ([PR #137926](https://projects.blender.org/api/v1/repos/blender/blender/pulls/137926)). After Effects keeps a global RAM cache of uncompressed layer and comp frames. Each frame is keyed by a hash of everything that affects its render, so an edit invalidates only the frames whose inputs changed. Since 25.2, AE also streams frames from a persistent disk cache, so preview length depends on disk size and speed rather than RAM ([Adobe 25.2](https://helpx.adobe.com/after-effects/desktop/using/whats-new/2025-2.html)). In Blender today, the closest you get to AE's "render once, play in real time" is a playblast to an image sequence, played in the VSE or Animation Player. To make the live viewport faster, you bake the heavy evaluation (simulations, the Geometry Nodes Bake node, Alembic/USD). The rest of this report explains how AE's cache decides what is valid, maps each Blender cache onto it, and sketches how a Python tool could close the gap.

## After Effects keys every frame to a render-state hash

AE's RAM cache is a **global, uncompressed frame cache**. It holds composited comp frames and also individual layer frames. Frames survive undo/redo and are reused across duplicated layers and duplicated comps. Frames that render quickly are deliberately not cached, which is why a comp of plain solids or text may never show a full green bar ([Adobe: Memory and storage](https://helpx.adobe.com/after-effects/using/memory-storage.html)). Green in the time ruler means a frame is in RAM, and blue means it is in the disk cache ([Adobe: Previewing](https://helpx.adobe.com/after-effects/using/previewing.html)). Because layers are cached individually, changing one layer re-renders only that layer, and the rest are read from cache and re-composited. Walter Soyka observed that a 10-layer, 100-frame comp can produce about 1,100 cache entries. That figure is an experienced user's observation, not Adobe documentation ([Creative COW](https://creativecow.net/forums/thread/disk-cache-setup-questions/)).

What makes this work is that **validity is hash-based, not timestamp-based**. The AE SDK says that since the CS6 Global Performance Cache, effects "must tell After Effects to discard old cached frames." SmartFX plugins mix custom state into a frame's GUID with `GuidMixInPtr()` (enabled by `PF_OutFlag2_I_MIX_GUID_DEPENDENCIES`). With that GUID, "AE can tell whether the frame already exists or if it needs to be rendered," and frames can be reused after an undo ([AE SDK Guide](https://ae-plugins.docsforadobe.dev/print_page/)). The persistent key also includes the **effect's version number and the AE build number**. Adobe tells developers to bump the plugin version when shipping a rendering fix, and to disable and empty the disk cache while iterating ([AE SDK: Tips & Tricks](https://ae-plugins.docsforadobe.dev/effect-details/tips-tricks/)). Time dependencies have to be declared. If an effect reads parameters or layers at other times without `PF_OutFlag_WIDE_TIME_INPUT`, "After Effects won't correctly invalidate cached frames." `PF_OutFlag_NON_PARAM_VARY` stops AE from caching output on stills, and `PF_OutFlag_I_EXPAND_BUFFER` "drastically reduces caching efficiency" ([AE SDK: PF_OutData](https://ae-plugins.docsforadobe.dev/effect-basics/PF_OutData/)). The Compute Cache API, added for Multi-Frame Rendering (MFR), works the same way. Keys are built with `AEGP_CreateHashFromPtr`/`AEGP_HashMixInPtr` from parameters and layer checkout hashes, and "the hash represents the inputs used to generate the frame, not the frame's pixels" ([AE SDK: Compute Cache API](https://ae-plugins.docsforadobe.dev/effect-details/compute-cache-api/)).

So an edit changes the hash of every frame and layer it feeds, and the change propagates to parent comps through the mixed-in checkout hashes. Undo restores the old hash, and the old frames become valid again at no cost. When a frame looks wrong but its bar is still green or blue, the usual cause is a third-party effect that under-declares its dependencies. Purge > All Memory & Disk Cache confirms it, and Alt/Option-clicking Purge > All Memory also resyncs the project database ([Adobe: Memory and storage](https://helpx.adobe.com/after-effects/using/memory-storage.html)). Expressions follow the same lifetime: simple property links are cached, and "values changing over time will have the same cache lifetime as rendered frames themselves" ([Adobe community, John Colombo](https://community.adobe.com/questions-529/do-expressions-use-caching-expression-performance-help-60706)). Adobe has never published the exact hash composition for native layers, so the per-layer and partial-range behavior is inferred from SDK semantics and user observation.

## Since 25.2, disk speed sets AE's preview length

The disk cache is a **persistent, cross-project frame store**. When a project opens, AE scans the cache and fills in blue marks for matching frames, including frames from other projects. Each AE version keeps its own cache, and Roto Brush frames are never persisted. The default size is 10% of the volume, capped at 100 GB, and AE needs 10 GB free beyond that maximum ([Adobe: Memory and storage](https://helpx.adobe.com/after-effects/using/memory-storage.html)). Adobe's Memory and storage page still says the disk cache "is not used for real-time previews." That has been outdated since **High Performance Preview Playback** shipped in 25.2 (April 2025). The feature is controlled by Preferences > Media & Disk Cache > Enable Preview from Disk Cache, which is on by default ([Adobe 25.2](https://helpx.adobe.com/after-effects/desktop/using/whats-new/2025-2.html)). It "writes every rendered frame to disk cache" and streams frames back into RAM ahead of the playhead. In Puget's test with RAM capped at 2 GB, 25.1 cached 46 of 413 frames, while 25.2 cached and played all 413 ([Puget, Feb 2025](https://www.pugetsystems.com/blog/2025/02/24/upcoming-boost-to-after-effects-preview-playback-with-ram-and-disk-cache/)).

That change moved the bottleneck from RAM to the cache drive. Uncompressed 8 bpc frames are about **7.91 MB at HD and 31.64 MB at UHD**. 4K24 needs about 759 MB/s sustained, which Gen4 NVMe can handle, while 8K30 exceeded Gen4 in testing. Puget advises keeping 30% of the drive free, because throughput drops as it fills ([Puget, Nov 2025](https://www.pugetsystems.com/labs/articles/how-disk-cache-impacts-after-effects-preview-playback/)). **Lossless Compressed Playback** (Enable Compressed Frames (Lossless)) reduces the footprint at a CPU cost. It supports all working bit depths but cannot store frames as 16-bit float ([Adobe beta announcement](https://community.adobe.com/announcements-532/now-in-beta-lossless-compressed-playback-in-after-effects-beta-314506)). The sources disagree on which release shipped it: CG Channel says 26.0 (January 2026) ([CG Channel](https://www.cgchannel.com/2026/01/adobe-releases-after-effects-26-0-with-native-substance-support/)), while Adobe's What's New groups it near 26.2 ([Adobe What's New](https://helpx.adobe.com/uk/after-effects/desktop/what-s-new/whats-new.html)). In 26.5 (September 2026), Object Matte propagation results also became disk-cached and persistent ([CG Channel](https://www.cgchannel.com/?p=178609)).

Two background mechanisms fill the cache. MFR has been on by default since 22.0 and renders frames in parallel, with Adobe quoting 1.75–2x speedups on 8–10 cores ([Adobe: MFR](https://helpx.adobe.com/after-effects/using/multi-frame-rendering.html)). **Cache Frames When Idle** renders the focused comp and its precomps after a configurable idle delay of 2–15 seconds ([Adobe beta forum](https://community.adobe.com/t5/after-effects-beta-discussions/speculative-preview-now-available-in-18-4x37/td-p/12131166/highlight/true)). Preview Resolution overrides comp resolution, so Half and Full frames are cached as separate entries ([Adobe: Previewing](https://helpx.adobe.com/after-effects/using/previewing.html)). The Media Cache (.cfa audio conforms and .mpgindex files) is a separate system, and **Clean Database & Cache never touches preview frames** ([Adobe: Memory and storage](https://helpx.adobe.com/after-effects/using/memory-storage.html)). In practice, put the disk cache on a dedicated NVMe drive and raise Maximum Disk Cache Size well above the 100 GB default. Since 25.2, preview length scales with that number.

## Blender's 3D Viewport stores no frames, only faster evaluation

Viewport playback in Blender is live evaluation and nothing more. The Sync options only choose how to fail when evaluation is too slow. **Play Every Frame** plays slower than real time. **Frame Dropping** and **Sync to Audio** keep timing correct by skipping frames ([Manual: animation_editors.rst](https://projects.blender.org/blender/blender-manual/raw/branch/main/manual/animation/animation_editors.rst)). The Timeline's Cache display shows physics and simulation caches, not pixels ([Manual: timeline.rst](https://projects.blender.org/blender/blender-manual/raw/branch/main/manual/editors/timeline.rst)). Blender Studio animators commissioned a "Faster Animation Playback" task in 2019. Its first milestone was an "Animation Cache" invalidated during animation, and its status remains "Discussing Designs" with no release target ([T68908](https://developer.blender.org/T68908)). The follow-up design, #73481, considered caching final depsgraph geometry, using the Mesh Sequence Cache modifier, or a hidden "virtual cache modifier." It is labelled "Initial, not validated" and has no assignee or milestone ([#73481](https://projects.blender.org/blender/blender/issues/73481)). The 5.2 and 5.3 animation notes cover loop modes and scrubbing UX, not frame caching ([5.3 Animation notes](https://projects.blender.org/blender/blender-developer-docs/raw/branch/main/docs/release_notes/5.3/animation_rigging.md)).

Blender has invested in evaluation speed instead. In 5.1, action evaluation on a 2,600-bone rig went from **32.8 to 74.1 fps**, and shape-key evaluation on a mesh of about 1M vertices went from **39.2 to 158.7 fps**. A real production file gained a more modest 14% ([5.1 Animation notes](https://projects.blender.org/blender/blender-developer-docs/raw/branch/main/docs/release_notes/5.1/animation_rigging.md)). Blender Studio's Sprite Fright tests point to the same levers. They used no caching. Bone and driver counts barely mattered. What mattered most was the **number of vertices deformed by Armature, Corrective Smooth, Shrinkwrap and Lattice modifiers**, and Simplify (with Subdivision Surface off) kept a single character at the 24 fps cap ([Blender Studio blog](https://studio.blender.org/blog/sprite-fright-scene-fps)). Visible Graph Editors and Dope Sheets also slow playback because their curves redraw every frame, which Active Editor Only redraw avoids ([#73429](https://projects.blender.org/blender/blender/issues/73429)).

Blender's native caches store **evaluated data, not pixels**. The Geometry Nodes Simulation Zone caches automatically during playback, shown as a purple timeline line, and can be baked to disk ([Manual: simulation_zone.rst](https://projects.blender.org/blender/blender-manual/raw/branch/main/manual/modeling/geometry_nodes/simulation/simulation_zone.rst)). The **Bake node** (4.1+) freezes any part of a node tree, animated or still, packed into the .blend or written to disk. The manual warns that a bake written by one Blender version is not guaranteed to load in another ([Manual: bake.rst](https://projects.blender.org/blender/blender-manual/raw/branch/main/manual/modeling/geometry_nodes/geometry/operations/bake.rst)). Physics point caches have the same RAM-or-disk choice, with Disk Cache requiring a saved .blend ([Manual: baking.rst](https://projects.blender.org/blender/blender-manual/raw/branch/main/manual/physics/baking.rst)). The Mesh Sequence Cache modifier swaps rig evaluation for Alembic or USD reads ([Manual: mesh_sequence_cache.rst](https://projects.blender.org/blender/blender-manual/raw/branch/main/manual/modeling/modifiers/modify/mesh_sequence_cache.rst)). For motion-graphics and explainer scenes heavy on Geometry Nodes, the Bake node gives the biggest live-playback win. Rigs, unbaked modifiers and viewport drawing still run every frame.

## The VSE and the 5.3 compositor are Blender's real RAM previews

The VSE is Blender's closest match to AE. Its cache stores preview frames in RAM, shows them on the timeline (a red bar for Raw, a blue bar for Final), and **prefetches** frames ahead of the playhead. Prefetch is "not supported for Scene strips" ([Manual: cache.rst](https://projects.blender.org/blender/blender-manual/raw/branch/main/manual/editors/video_sequencer/sequencer/sidebar/cache.rst)). Aras Pranckevicius rewrote the cache for 4.5 (PR #137926, merged May 14, 2025), and the rewrite changed several things older tutorials still describe. There are now two cache types instead of four. The **Source (raw)** cache is keyed by strip and content frame. The **Final** cache is keyed by timeline frame and invalidated when any overlapping strip changes. An intra-frame cache holds only the current frame. **The disk cache was removed outright.** The author considered it redundant with proxies, it was off by default and never covered scene strips, and stale data was a risk. The RNA properties `use_sequencer_disk_cache`, `sequencer_disk_cache_dir`, `sequencer_disk_cache_size_limit` and `sequencer_disk_cache_compression` no longer exist. Invalidation had been a bottleneck, so the rewrite also cut scene-strip frame time from **265 ms to 60 ms** in a test ([PR #137926](https://projects.blender.org/api/v1/repos/blender/blender/pulls/137926); [4.5 Sequencer notes](https://projects.blender.org/blender/blender-developer-docs/raw/branch/main/docs/release_notes/4.5/sequencer.md)).

That settles a conflict between sources. Treat any tutorial, add-on or script that points to Preferences > System > Sequencer Disk Cache as **applying only to Blender 4.4 and earlier**. That includes Blender's own developer "Sequencer Cache" design page, which still describes the disk cache ([Developer docs: Sequencer Cache](https://developer.blender.org/docs/features/sequencer/cache/)). The common advice to raise the **Memory Cache Limit** is still correct, but it now controls RAM only. The setting lives in Preferences > System > Video Sequencer, and the manual "recommends high values" ([Manual: system.rst](https://projects.blender.org/blender/blender-manual/raw/branch/main/manual/editors/preferences/system.rst)). Since 4.5 it limits only the sequencer caches, where before it stopped caching once the whole Blender process reached that size ([PR #137926](https://projects.blender.org/api/v1/repos/blender/blender/pulls/137926)). The 5.x default is unconfirmed. So is whether the Movie Clip Editor's cache still shares that limit after the rewrite. Later releases improved the VSE further. 5.0 turned prefetch on by default and made it loop-aware ([5.0 Sequencer notes](https://projects.blender.org/blender/blender-developer-docs/raw/branch/main/docs/release_notes/5.0/sequencer.md)). 5.2 stopped clearing Final caches after a render and prefetches five frames behind the playhead ([5.2 Sequencer notes](https://projects.blender.org/blender/blender-developer-docs/raw/branch/main/docs/release_notes/5.2/sequencer.md)). The 5.3 beta adds hardware video decoding, though the notes concede the VSE is "still heavily CPU-dependent" ([5.3 Sequencer notes](https://projects.blender.org/blender/blender-developer-docs/raw/branch/main/docs/release_notes/5.3/sequencer.md)).

Users often try a Scene strip as a RAM preview of a live 3D shot. It works, but badly. Because prefetch skips scene strips, the community workaround is to set Play Every Frame, play the range once so every frame lands in the Final cache, and keep ranges short ([BlenderArtists](https://blenderartists.org/t/how-to-load-scene-strip-to-cache-for-preview-vse/1244416)). Since 4.5, scene strips are invalidated when the rendered scene changes ([4.5 Sequencer notes](https://projects.blender.org/blender/blender-developer-docs/raw/branch/main/docs/release_notes/4.5/sequencer.md)). Developers have attributed the long-standing slowness of EEVEE scene strips to GPU-to-CPU readback that needs a large overhaul to fix, and their recommended workaround is pre-rendering ([T62517](https://developer.blender.org/T62517)).

The compositor is getting a cache for the first time. 5.2 added playback to the interactive compositor ([5.2 Compositor notes](https://projects.blender.org/blender/blender-developer-docs/raw/branch/main/docs/release_notes/5.2/compositor.md)). Omar Emara's **Frame Cache** (PR #159902, merged June 18, 2026, shipping in 5.3) caches the final viewer result per frame under the Memory Cache Limit, displays it on the timeline, and temporarily suspends playback so the whole range gets computed. Its invalidation is much coarser than AE's: **any change to the node tree clears the entire cache**, and it does not cover the viewport compositor or VSE compositor modifiers ([PR #159902](https://projects.blender.org/api/v1/repos/blender/blender/pulls/159902)). Per-node result caching, which would be the AE-like granularity, is still only an idea under discussion ([devtalk, Feb 2026](https://devtalk.blender.org/t/2026-02-26-compositor-meeting-notes/44473)).

| Capability | After Effects (26.x) | Blender (5.2 LTS / 5.3 beta) |
|---|---|---|
| Rendered-frame RAM cache | Global, per-layer and per-comp | VSE Raw and Final; compositor Frame Cache (5.3); Animation Player; **none in 3D Viewport** |
| Persistent disk cache | Yes, cross-project, streamed during playback (25.2+) | **None since 4.5**; playblast files are a manual substitute |
| Invalidation | Per-frame input hash; undo restores frames | VSE: frames overlapping an edited strip; compositor: whole cache on any edit; playblast: none |
| Background fill | MFR plus Cache Frames When Idle | VSE prefetch (not Scene strips); compositor fills the range |
| Plugin participation | SDK flags, GUID mixing, Compute Cache | Not applicable |

## Playblast plus a RAM-caching player is today's workable answer

The native route that works most like AE is View > **Render Playblast**, the 5.2 manual's name for Viewport Render Animation. It renders Workbench or EEVEE to an image sequence. Cycles is not supported ([Manual: viewport_render.rst](https://projects.blender.org/blender/blender-manual/raw/branch/main/manual/editors/3dview/viewport_render.rst)). You then play the result in the Animation Player (Ctrl-F11), which caches frames up to the Memory Cache Limit ([Manual: animation_player.rst](https://projects.blender.org/blender/blender-manual/raw/branch/main/manual/render/output/animation_player.rst)), or as an Image strip in a VSE scene, where prefetch applies. The files on disk act as a persistent cache that you manage yourself. To re-render a sub-range by hand, overwrite just those frames and reload the strip. Sizing follows AE's arithmetic: a 1080p 8-bit frame is about 8 MB in RAM, so a 10-second shot at 24 fps needs roughly 2 GB ([Puget](https://www.pugetsystems.com/labs/articles/how-disk-cache-impacts-after-effects-preview-playback/)).

Add-ons improve the ergonomics but keep the same "render everything, then watch" model. **Anim Reviewer** is free, supports 4.2 LTS and later, and was updated August 2026. It makes encoded previews with burn-ins and per-preview overrides ([extensions.blender.org](https://extensions.blender.org/add-ons/anim-reviewer/)). **Flipbook** ($15, Blender 5.0) captures Solid, Material Preview or EEVEE to EXR, PNG or JPEG, and refreshes its player in place after a re-render ([Superhive](https://superhivemarket.com/products/flipbook/docs)). Blender Studio's **Blender Kitsu** versions its playblasts, saves .blend backups, and loads them into a VSE review scene. It is the most production-tested pattern found, and it fits a pipeline that already runs Flamenco ([Blender Studio](https://studio.blender.org/tools/addons/blender_kitsu)). The only true in-viewport cache found is **Animation Cache** ($25, Blender 3.4–5.0). It records object and bone transforms and plays them back from memory. Its author says any edit makes the cache stale until it is rebuilt, and it does not say whether it handles shape keys or modifiers, so test it on deforming rigs before relying on it ([Superhive](https://superhivemarket.com/products/animation-playback-cache/docs)). VCache's ffmpeg-based "fill missing frames" is the nearest thing to partial re-caching, but the project shows little activity ([GitHub](https://github.com/samytichadou/vcache)).

No shipped tool does AE-style incremental invalidation, but the Python API has the pieces to approximate it. A `depsgraph_update_post` handler can read `depsgraph.updates` to see which IDs changed and whether the change touched geometry, shading or transform ([API: DepsgraphUpdate](https://docs.blender.org/api/current/bpy.types.DepsgraphUpdate.html); [API: bpy.app.handlers](https://docs.blender.org/api/current/bpy.app.handlers.html)). From that, the tool marks a frame range dirty: the span of an edited F-curve's keys when the change is local in time, or the whole range for material, world or modifier edits. `bpy.ops.render.opengl` with `write_still` renders only those dirty frames into a cache folder ([API: render operators](https://docs.blender.org/api/current/bpy.ops.render.html)). A VSE Image strip reloads only those files, and a timeline draw handler can paint an AE-style status bar. For per-frame validity, hash the camera matrix and lens, each object's world matrix, and a strided sample of evaluated vertex positions. This copies AE's "hash the inputs, not the pixels" idea from the Compute Cache API, but computing the hashes costs roughly one full evaluation pass. The design has hard limits. Python and the depsgraph run on the main thread, so filling the cache makes the UI stutter. Simulations with history make frames depend on earlier frames. Shading-mode or view changes invalidate everything. These API details come from index pages that could not be fully read for 5.x, so check the signatures against the current API before building on them. The 2019 GSoC proposal named exactly this problem, re-caching only the 5 of 100 frames an edit touches, as the hard part ([bf-committers](https://lists.blender.org/pipermail/bf-committers/2019-February/049805.html)).

## Conclusion

The real difference is the cache key, not the RAM or disk size. AE can cache aggressively and keep the cache across sessions because every node in its render graph has a content hash. That design runs from the CS6 Global Performance Cache to `GuidMixInPtr` and the Compute Cache API, and it is why AE plugin authors must declare time and non-parameter dependencies honestly. Blender's 2D caches use coarse keys. The VSE invalidates by strip overlap, and the compositor clears everything on any edit. Blender dropped its only persistent pixel cache rather than risk stale frames. Without hashes, persistence is dangerous, so the 4.5 removal fits. It also suggests Blender will not get an AE-grade viewport cache until something like #73481's depsgraph-level geometry caching exists, and nothing on record schedules that.

For a studio that uses both applications, AE's 25.2+ caching rewards spending on a fast, roomy NVMe cache drive more than on extra RAM. In Blender, the practical step is to bake evaluation and playblast to sequences played from a RAM cache, not to wait for a viewport cache. Treat anything that tells you to configure a Blender disk cache as written for 4.4 or earlier. The open opportunity is a hash-based incremental playblast tool. It would bring AE's "re-render only what changed" model to Blender, and the API already supports it.
